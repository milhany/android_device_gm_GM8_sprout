## Bluetooth still needs the immediate pre-abort message

There are 30 native com.android.bluetooth aborts, including failures on October
20 at 09:10. They all report alarm.cc:169. In the matching Lineage 19.1 source,
alarm_new_internal aborts when lazy_initialize fails. That function has several
failure paths (timer creation, semaphore/thread/queue allocation); the stack
alone does not distinguish them. Bluetooth uses FIFO-priority SIGEV_THREAD
timers. The old kernel also enables RT_GROUP_SCHED while the new CPU groups
have no device-defined RT budgets. This is a scheduling hypothesis to verify,
not an established timer errno from the supplied log.

Capture live main/system/crash buffers while enabling Bluetooth once, retaining
the error preceding alarm.cc:169. Also inspect zygote membership and the
foreground/top-app cpu.rt_runtime_us values before changing RT policy or clock
selection. Do not remove the fatal assertion, silently fall back to a different
clock, or disable Bluetooth to hide the crash.
