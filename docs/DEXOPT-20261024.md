# TikTok full-compilation timeout

The October 24 controlled `cmd package compile -m speed -f` capture establishes
why this attempt failed. It is not a successful compilation with noisy warnings:

- The base APK completes in 206.491 seconds and installd reports success.
- The code split starts at 18:46:45. ART's own watchdog terminates it at
  18:56:15 with `dex2oat did not finish after 570 seconds`.
- installd reports process status 0x100 / error 256. The command reports Failure.
- The final package state is `speed / cmdline` for the base APK and
  `run-from-apk / unknown` for `split_df_a_dex.apk`.
- The entire package operation lasts 780859 ms, followed by a PackageDexOptimizer
  wake-lock timeout warning. This is not a system-server watchdog reboot.

The earlier installation failure has the same wrapper error, but its retained
log lacks the compiler's fatal message. Do not assume it necessarily has the
same underlying cause. Nor does this test identify the exact compiler pass or
method responsible for exhausting the time budget.

`Accessing hidden method (... blocked, linking, denied)` is not the fatal event
in this capture. A running compiler and available memory in one top/meminfo
sample did not rule out its later watchdog timeout. Low-memory events also
occur later in the complete capture; there is no compiler OOM fatal message.
The compiler's 32-bit executable producing arm64 output is supported behavior,
not by itself an ABI mismatch.

## Device policy change

Set `pm.dexopt.install` and `pm.dexopt.bg-dexopt` to `speed-profile`, matching
LineageOS Android 12.1 `target/product/runtime_libart.mk`. Installs can use
profiles supplied with dex metadata; later idle background optimization can
use the collected runtime profile. Avoid forcing every method of every app
through full `speed` compilation on this Cortex-A53 device.

This reduces compilation scope; it is not a repair of ART's full-speed compiler
and does not guarantee a particular TikTok launch time, video frame rate or ANR
result. Useful AOT coverage depends on the available profile. A normal install
and the platform's background job manage future optimization automatically.

These system properties require a full ROM update, not only boot.img. Reuse
the existing release keys; no Format Data is required solely for this change.
Updating properties does not immediately recompile existing packages.

## Focused on-device check before a new ROM build

To test profile compilation of only the failed split without forcing another
base-APK compilation, run once from the Windows platform-tools directory:

```bat
adb shell cmd package compile -m speed-profile -f --split split_df_a_dex.apk com.zhiliaoapp.musically
adb shell dumpsys package dexopt > gm8-dexopt-profile.txt
```

On this Android 12.1 PackageDexOptimizer implementation, `--split` compares the
APK filename, including `.apk`, rather than the manifest split name. Verify
that the split's package state changes; a bare Success string alone is not
sufficient. No profile clearing, application-data reset or verification bypass
is involved. This is a diagnostic check, not a required per-app user workflow.

Then compare cold launch and video behavior. If the broadcast ANRs continue,
collect a bugreport containing the matching ANR thread traces; compilation
failure alone does not establish the cause of those ANRs.

## Follow-up: profile compilation and launch test

The split-only command actually invokes dex2oat with `speed-profile` and a
profile-file descriptor. It finishes in 75.198 seconds and installd reports
success. The retained 570-second fatal message predates this successful test.
The later runtime excerpt spans approximately 19:06:53-19:09:13, with no new
TikTok ANR, Java fatal exception or native fatal signal. This short window
does not establish a permanent ANR repair.

Four new process launches report Displayed times of 4.768, 5.248, 5.665 and
5.266 seconds. They are not a controlled comparison with an older app version
or cache state. Each process is subsequently killed for `remove task`; these
are not evidence of spontaneous process crashes or low-memory kills.

## Follow-up: performance trace

The original trace has approximately 27.9 seconds of trace bounds. Its
Android frame-timeline data is readable, but the Android 12 recorder omits
legacy ftrace clock metadata: 686186 kernel events are initially discarded as
preceding the tracing start. Direct parsing therefore reports zero sched rows
and cannot support a CPU diagnosis by itself. The ring buffer also overwrote
approximately 5.8 MB, so complete capture coverage must not be assumed.

For local analysis only, a separate copy annotates its 1414 ftrace bundles
with a legacy GLOBAL clock and the trace's MONOTONIC/BOOTTIME snapshot pair.
The two snapshot offsets agree within 1.4 microseconds. This recovers about
203000 sched rows and the application atrace slices. The original upload is
untouched. The exact GLOBAL-to-MONOTONIC offset was not recorded on-device;
cross-clock alignment remains approximate. Durations between events within
the original ftrace clock do not depend on the constant offset. Nine scheduler
tid-mismatch diagnostics remain, and timing conclusions must respect these
capture limitations.

Observed within the recovered application events:

- An initial UI Choreographer frame lasts about 1016 ms; its traversal is
  about 1012 ms and its nested measure slice about 648 ms. These overlap;
  do not add the durations together.
- Library-loading and WebView initialization workers have monitor-contention
  waits of approximately 0.95-1.00 seconds. These are not all main-thread
  waits and must not be added to the launch duration.
- The main thread has about 7.65 CPU seconds, 0.23 seconds runnable waiting
  and 2.07 seconds in D/DK states in the retained coverage. D/DK alone does
  not prove storage I/O; blocked-function and io-wait annotations are absent.
- CPU frequency samples reach 1401000 kHz on CPUs 0-3 and 1094400 kHz on
  CPUs 4-7. The trace does not show the CPU being permanently stuck at its
  minimum frequency. This is not a thermal-throttling exclusion test.
- The main activity layer's original frame-timeline data contains 285
  records, of which 145 are Late Present. This is a UI-layer result, not a
  count of dropped video frames or a measured video FPS.

The media dump confirms Qualcomm hardware HEVC decoding. A 576x1024 session
reports latency.avg=679822 us, but only 15 matched samples and 394 unknown
samples. MediaCodec measures input-to-output buffer round trips, including
pipeline residence; unknown timestamps are not a dropped-frame count. These
numbers cannot establish standalone decoder throughput or displayed FPS.
See android_frameworks_av, lineage-19.1, media/libstagefright/MediaCodec.cpp,
statsBufferReceived for the measurement semantics.

The confirmed correction is profile-based compilation scope. UI startup,
resource/class loading, synchronization and video presentation remain separate
performance work. These captures do not justify a new GPU blob change, broad
SELinux grants, disabled thermal protection or increased ART watchdog limits.
